# 코드 흐름 문답 리뷰

## The Insight

코드 리뷰는 "코드를 읽는 것"이 아니라 **"흐름을 납득하는 것"**이다.
함수명과 모듈명을 나열하는 것보다, 각 단계에서 "왜 이렇게 동작하는가"를 설명하고
사용자가 납득하지 못하면 즉시 개선하는 방식이 실제 문제를 발견하는 데 훨씬 효과적이다.

## Why This Matters

- 단순 코드 리뷰: 문서 작성 → 혼자 읽음 → 놓치는 케이스 많음
- 문답 방식: 설명 → 반박 → 개선 → 다음 단계로 진행 → 실제 버그/설계 결함 발견률이 높음

## Recognition Pattern

사용자가 다음 중 하나를 요청할 때:
- "코드 흐름대로 설명해줘"
- "납득시켜봐"
- "순서대로 문답하자"
- 다이어그램을 보면서 로직을 점검하고 싶을 때

## The Approach

### 세션 시작 시

1. **대상 확인**: 어떤 모듈/기능의 흐름을 다룰지 파악
2. **흐름 순서 결정**: 다이어그램이 있으면 그 순서대로, 없으면 진입점(entry point)부터 시작
3. **규칙 안내** (첫 메시지에):
   > "다이어그램 흐름대로 하나씩 설명하겠습니다. 납득되면 '다음'이라고 하시고, 의문이 있으면 바로 질문해 주세요. 문제가 발견되면 즉시 코드를 수정합니다."

### 각 Step 설명 형식

```
## Step N — ModuleName.function_name()

**위치:** 파일명.py > 클래스명 (없으면 모듈 레벨)

[함수가 하는 일을 2~4줄로 설명]

**주의할 점 / 특이사항:**
- [놓치기 쉬운 동작, 엣지 케이스, 설계 의도]

---
납득되시나요?
```

### 문답 처리 규칙

| 사용자 반응 | 행동 |
|---|---|
| "다음" / "ㅇㅇ" / "납득" | 다음 Step으로 이동 |
| 질문 / 의문 제기 | 코드를 직접 읽어서 정확하게 답변 |
| "이상한데" / "문제있어" | 코드 확인 → 문제 인정 시 즉시 수정 제안 |
| "수정해줘" | 바로 Edit 도구로 수정, 수정 후 다음 Step 계속 |
| "삭제해줘" | 해당 로직 제거 후 계속 |

### 설명 시 반드시 포함할 내용

- **정확한 위치**: `파일명.py` + `클래스명.메서드명()` + 라인 번호
- **실제 동작**: 추상적 설명 금지, 코드에서 확인된 사실만
- **엣지 케이스**: 실패 경로, 예외 처리, 타임아웃 등
- **외부 의존**: 이 함수가 호출하는 다른 모듈/서비스

### 하지 말아야 할 것

- ❌ 코드를 읽지 않고 기억으로 설명 → 반드시 Read/Grep으로 확인 후 설명
- ❌ "아마도", "보통은" 같은 추측성 설명
- ❌ 사용자가 납득하지 않았는데 다음 Step으로 넘어가기
- ❌ 문제를 발견했는데 나중에 고치겠다고 미루기 → 즉시 수정

## Example

```
## Step 3 — DebateEngine._wait_for_local_agents()

**위치:** engine.py > DebateEngine 클래스 (line 171)

로컬 에이전트(provider="local")가 있을 때만 실행됩니다.
match.status를 "waiting_agent"로 변경 후 SSE 발행하고,
ws_manager.wait_for_connection()으로 WebSocket 접속을 기다립니다.

**주의할 점:**
- debate_agent_connect_timeout(30초) × debate_agent_connect_retries(3회) = 최대 90초 대기
- 3회 모두 실패 시 ForfeitHandler.handle_disconnect() → 몰수패 처리
- 크레딧 차감(_deduct_credits)은 이 단계 이후 → 접속 실패 시 크레딧 차감 없음

---
납득되시나요?
```

### 이해도 스코어링

각 Step 설명 후 사용자 반응을 3단계로 추적한다:

| 반응 | 점수 | 트리거 |
|------|------|--------|
| **명확** | 1.0 | "다음", "ㅇㅇ", "납득" |
| **질문있음** | 0.5 | 질문/의문 제기 후 답변으로 해결 |
| **이해불가** | 0.0 | 같은 Step에서 3회 이상 질문, 또는 "모르겠다" |

세션 종료 시 이해도 리포트를 생성한다:
```
이해도 리포트:
  전체 평균: {avg:.1f}/1.0
  명확: {n}개 함수 | 질문있음: {n}개 | 이해불가: {n}개

  ⚠️ 이해 부족 함수:
  - Step 3: DebateEngine._wait_for_local_agents() — 0.0 (3회 질문)
  - Step 7: TurnExecutor._call_llm() — 0.5 (타임아웃 로직 질문)
```

### 북마크 기능

사용자가 "여기 중요", "북마크", "기억해둬" 라고 하면 해당 함수를 북마크한다.
메모를 함께 남길 수 있다: "여기 중요 — 나중에 리팩토링 필요"

세션 종료 시 북마크 요약을 생성한다:
```
북마크 목록 (3개):
  ★ Step 2: DebateEngine._load_entities() — "DB 쿼리 최적화 필요"
  ★ Step 5: TurnExecutor.execute_with_retry() — "재시도 로직 검토"
  ★ Step 8: FinalizeHandler.finalize() — (메모 없음)
```

### Conditional Branch 추적

함수에 `if/else`, `try/catch`, `match/case` 등 분기가 있을 때:

1. 분기점을 명시한다:
   ```
   이 함수에 분기가 있습니다:
   (A) 정상 경로 — provider="api"일 때 LLM 호출
   (B) 에러 경로 — provider="local"일 때 WebSocket 대기
   (C) 예외 경로 — 타임아웃 시 몰수패 처리

   어떤 경로를 먼저 살펴볼까요?
   ```

2. 선택한 경로를 설명하고, 다른 경로는 `[?]`로 표시:
   ```
   진행: [✓] run [✓] load [▶] wait(A경로) [?] wait(B경로) [ ] execute
   ```

3. 현재 경로 설명 후 "다른 경로도 볼까요?" 선택지를 제공한다.

세션 종료 시 미탐색 분기 목록을 표시한다:
```
미탐색 분기:
  - Step 3: _wait_for_local_agents() — B경로 (WebSocket 실패 시)
  - Step 6: _call_llm() — C경로 (rate limit 초과 시)
```

### 스킬 핸드오프

워크스루 중 사용자가 "이 함수 문제있어", "이거 고쳐야 해", "버그 같다" 라고 하면:

```
이 함수에 문제가 발견되었습니다. 어떻게 하시겠습니까?

1. auto-walkthrough로 4에이전트 자동 분석 → 수정안 제시
2. code-audit-interview로 이 함수 집중 감사
3. 북마크 후 워크스루 계속 (나중에 처리)
```

- 선택 1, 2: 현재 워크스루 상태를 `state_write`로 저장 후 해당 스킬 호출
- 선택 3: 북마크에 "문제 발견" 메모 추가 후 다음 Step 진행

핸드오프 이력은 세션 종료 요약에 포함한다.

## 세션 종료 조건

- 다이어그램의 마지막 Step까지 모두 완료
- 또는 사용자가 "여기까지" / "종료" / "끝내자" 라고 할 때
- 종료 시: 이번 세션에서 수정된 항목 목록을 요약 제공
